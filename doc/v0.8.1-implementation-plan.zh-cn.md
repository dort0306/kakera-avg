# v0.8.1 KPAK 2 流式资源包

制定日期：2026-10-25，先于本版功能代码。用户明确要求新增面向大体积游戏的 KPAK 2，并保留 KPAK 1 兼容。这是 v0.8 单一旧格式清理规则的明确例外，仅限资源包，不恢复旧 story/UI/save。

## 方案与边界

- 版本 0.8.1；story 8 / UI 3 / save 8 / content-version 8 不变。XML/JS 无法实现宿主文件偏移读取与解压，因此仅扩展 ContentSource、资源包及打包/视频字节入口，创作接口不变。
- KPAK 1 字节格式和读取器保持不变，适合小包；播放器按头中版本自动选择 1/2。新打包默认 2，可 --format 1 显式生成小包。发布仍不回退散文件。
- KPAK 2 为 80 字节固定头 + 独立 Zstandard 数据块 + 尾部未压缩索引。偏移/文件长度为 u64；固定 1MiB 原文块，块级去重、SHA-256、索引摘要、确定性。启动只读取头/索引，每个流只保留当前块，不整包解压或 mmap。
- 打开时校验索引/路径/引用/布局/预算，按需读取时验证每块后才交给消费者；--check 与打包验证显式扫描全部唯一块。未访问数据的损坏只能在访问或完整检查时发现，不把惰性打开说成全包验证。
- 预算：包及逻辑总量最多 1TiB、单文件 64GiB、100000 文件、1048576 唯一块、索引 128MiB，路径 1024 字节；单压缩块最多 2MiB，原文最多 1MiB。拒绝尾随帧/数据、洞/重叠、孤立块、非法引用、长度溢出和解压越界。
- ContentSource 新增受约束 open/copy_to；原 read 仍有 128MiB 内存上限，图像/字体/音频/模型原有解码预算不扩大。视频流式复制到后端临时文件，不再将完整视频放入 Vec；视频时长、尺寸、PCM 缓存等预算不变，不宣称直接从包 seek 解码。
- 工程/打包候选以私有磁盘暂存建立固定快照，逐块复制与哈希，不再用全量内存快照限制大工程。提交前重新扫描原工程完整指纹；剧本链只改暂存，候选和输出包完整校验成功后才原子提交。无异步 runtime、无绘制 IO。
