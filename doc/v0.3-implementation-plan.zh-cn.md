# v0.3 落地策略：变量与条件路由

制定日期：2026-10-23。基线为原始 MVC 方案与已验收 v0.2。用户已明确：本版先完成声明式规则；后续规则确实不足时使用 JavaScript，运行时选 QuickJS。本版不新增脚本运行时依赖。

## 1. 领域边界与数据

- story XML schema 3 新增 variables；原 schema 1/2 继续支持。flow schema 2 增加条件与更新，原 schema 1 继续支持。schema 3 的故事可使用旧 flow；有新规则的 flow schema 2 只允许与 story schema 3 配套。
- 变量仅有 int（i64，可配置 min/max）、bool（true/false）、string（最多 4096 UTF-8 字节）；不隐式转换，不支持浮点、动态声明、字符串插值、随机、时间或 IO。最多 128 个变量，变量 ID 为 1–64 个 ASCII 字母/数字/下划线，首字符为字母或下划线，可选 label 用于历史窗口中的状态展示。
- Model 保存声明、条件树、更新及当前值。规则求值放入独立的领域子模块 `model/rules.rs`，不引用应用其他模块；controller 仍只依赖 model，view 只读可用选项，App 在成功提交后才重置逐字/音频。
- 每次输入读取当前变量，先判定条件，选定目标，再在副本顺序执行更新，最后与场景/历史一起提交。未知变量、类型错误、整数溢出、越界或无效目标全部失败，原 Session 保持不变。

## 2. XML 契约

```xml
<variables>
  <int id="trust" label="信任" initial="0" min="0" max="3" />
  <bool id="met" label="已相识" initial="false" />
  <string id="mood" label="心情" initial="平静" />
</variables>
```

flow 的 next/on/case/otherwise 可含一个 effects：

```xml
<on option="accept" to="walk">
  <when><cmp var="trust" op="lt" value="3" /></when>
  <effects>
    <add var="trust" value="1" />
    <set var="met" value="true" />
    <set var="mood" value="期待" />
  </effects>
</on>
```

when 中恰好一个表达式：`cmp`、`all`、`any` 或 `not`。all/any 至少一个子表达式，not 恰好一个。cmp 将变量与同类型常量比较：int 支持 eq/ne/lt/le/gt/ge；bool/string 仅 eq/ne。表达式深度最多 16，每个条件最多 128 节点，每条更新列表最多 128 项。set 适用于三种类型，add 仅适用于 int（负值表示减法），按列表顺序执行。

选项的 when 在更新前求值；false 时隐藏，伪造选择同样被控制器拒绝。若当前没有可用选项，界面明确提示读档/重新开始。next 不接受 when，避免无去向；条件分流使用 branch。

```xml
<branch from="decision">
  <case to="accept">
    <when><all>
      <cmp var="trust" op="ge" value="2" />
      <cmp var="met" op="eq" value="true" />
    </all></when>
    <effects><set var="mood" value="开心" /></effects>
  </case>
  <otherwise to="refuse" />
</branch>
```

branch 至少一个 case，恰好一个 otherwise 且在最后；按 XML 顺序选择第一个满足的 case，没有命中则 otherwise。所有 case 的条件均基于提交前变量，只有命中分支执行更新。分流由一次 Advance 进入目标，branch 所属 Frame 本身正常显示，不在绘制期间自动穿越多个节点。

加载器保留严格的未知元素/属性、重复 ID、引用/类型与位置诊断；检查所有条件和更新，不因短路或不可达而忽略错误。非法的 set 常量在加载时拒绝；动态 add 在运行时做 checked_add 与声明范围检查。可达性警告使用所有潜在分支边，不尝试穷举变量状态。

## 3. 历史、存档及原子性

Session 新增 variables 与 history_base_variables。前者为当前值，后者为保留历史第一条进入时的变量检查点。历史仍最多 1000 条，只保存 frame_id/choice_id；裁掉第一条时，先用其决策推进变量检查点，再移除记录。

存档 schema 升级为 3，写入两份变量表。读档验证声明与变量键完全匹配、类型/范围合法，从检查点重放保留历史的条件、目标和更新，验证终点变量精确等于 variables。这样可检查条件与历史的一致性，又无需每条历史复制全部变量。重放只计算纯状态，不执行音频、逐字或 IO；不是防篡改签名系统，截断检查点的来源不做密码学认证。

schema 2 槽位允许在无变量故事中只读转换到内存 schema 3；有变量故事明确拒绝旧档，不能凭当前位置猜出变量。schema 1 的显式导入同样仅对无变量故事开放。旧文件不自动改写，用户再次手动保存才写新格式。六槽文件名和原子写入方式不变；坏档不影响当前位置、历史、变量或音频。

样例剧情改变了分支语义，保留故事 ID 但将 content-version 提升为 2，明确拒绝 v0.2 示例旧档。本版没有通用旧内容迁移。

## 4. 可运行样例与界面

将 games/demo 升级为七场景：opening → question；可多次选择散步增加 trust，达到 2 且 met=true 后显示邀请选项；到 decision 按 invited/trust 进入 accept、friendly、refuse 三种结尾。trust 达上限后隐藏散步，初始结束走 fallback，一次散步后结束走普通条件，达到阈值并邀请走优先条件。

逐字完成前所有选项保持原有门控；完成后只显示满足条件的选项，View 不求值副作用、不修改变量。历史窗口增加当前变量的 label/值，便于玩家核对选择结果与读档恢复；历史条目仍使用静态台词和当时已选项，不根据当前条件隐藏过去记录。重新开始恢复声明初值。

## 5. JavaScript / QuickJS 后续约定

本版的比较、组合条件、顺序赋值/加减和优先分支足以表达样例，因此不嵌入解释器。未来出现确实难以用上述数据表达的计算时，统一使用 JavaScript + QuickJS：脚本输入仅为可序列化的只读上下文，输出为经过 Rust 校验的路由结果或显式更新；不能持有窗口、纹理或可变 Model。仍由 Rust 原子提交并保存状态，不能把 JS 堆/闭包/调用栈当存档。

实际嵌入时再评估 Rust 绑定与 Windows 构建、许可证、CPU/内存限额、异常诊断、确定性、可用全局对象及宿主能力，给出规则不足的具体案例与测试；当前不预留空运行时、不假装已经具备 JS 执行能力。`<script>` 继续作为未知元素拒绝。
