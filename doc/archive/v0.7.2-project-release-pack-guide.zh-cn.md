## 1. 从运行 demo 到生成发布包

从源码构建需要 Rust stable（最低 1.88）、MSVC C++ 工具和 Windows 系统媒体组件。已有播放器/打包工具时可直接运行 exe，游戏作者无需修改 Rust。

```powershell
# 构建播放器与打包工具
cargo build --locked --release --bins

# 先检查，再进入带热更新的工程模式
./target/release/kakera-avg.exe --project games/demo --check | Out-Host
./target/release/kakera-avg.exe --project games/demo --save-dir target/demo-dev-saves
```

关闭上面的测试窗口后，生成资源包并检查发布模式：

```powershell
./target/release/kakera-pack.exe games/demo target/demo-release/game.kpak
./target/release/kakera-avg.exe --package target/demo-release/game.kpak --cubism-core runtime/live2d/windows-x64/Live2DCubismCore.dll --check | Out-Host
./target/release/kakera-avg.exe --package target/demo-release/game.kpak --cubism-core runtime/live2d/windows-x64/Live2DCubismCore.dll --save-dir target/demo-release-saves
```

首次生成时输出不能已存在；更新已有包需显式加 `--force`。上述 demo 使用真实 Live2D，因此发布检查显式传入仓库中的 Core。只生成 KPAK 不会自动复制播放器或 DLL；完整便携目录的制作见第 6 节。

也可以通过 Cargo 运行同一程序：

```powershell
cargo run --locked -- --project games/demo
cargo run --locked --bin kakera-pack -- games/demo target/demo-release/game.kpak --force
```

`cargo run` 的 `--` 之后才是播放器参数；指定 `--bin kakera-pack` 才会运行打包工具。

## 2. 工程目录与三种路径

建议只把游戏内容放入独立目录，例如 `games/my-game`，不要直接把整个 Rust 仓库作为游戏工程。

```text
games/my-game/
  story.xml                 固定入口名
  chapters/                 每份剧本显式 next，最后 end="true"
    first.xml
    ending.xml
  ui.xml                    文件名由 story.xml 的 interface 指定
  scripts/
    story.js                由 scripts 显式登记
    ui.js
  assets/
    bg/
    characters/
    fonts/
    audio/
    video/
    live2d/
    licenses/               字体、模型等素材许可
```

| 路径种类 | 相对基准 | 示例 |
| --- | --- | --- |
| 命令行工程、包、DLL、存档路径 | 当前 PowerShell 工作目录；也可传绝对路径 | `--project games/demo`、`--save-dir target/dev-saves` |
| XML/JS 清单、素材内容路径 | 游戏根目录；不随引用文件的子目录改变 | `<image id="bg.room" src="assets/bg/room.png" />` |
| model3 内部引用 | model3.json 所在目录，最终仍须留在游戏根内 | `textures/texture_00.png` |

next.src 同样以游戏根为基准，例如章节 first.xml 继续到 ending.xml 时写 `chapters/ending.xml`，不写 `ending.xml`。新剧本每份文件根为 story schema 7；只有入口有工程身份/entry/interface，后续文件可分工编写资源、视觉、变量、场景和脚本清单。完整三文件示例见 [API 第 21 节](xml-js-api.zh-cn.md#21-多文件剧本与打包合并)。

内容路径统一 `/`，区分大小写并禁止大小写碰撞；不使用盘符、绝对路径、反斜杠、空段、`.`、`..`、尾随点/空格或 Windows 特殊路径字符。被扫描的工程内容不允许符号链接。命令行路径可使用正常 Windows 路径；有空格时加引号：

```powershell
./target/release/kakera-avg.exe --project "D:/AVG Projects/My Game" --save-dir "D:/AVG Saves/My Game"
```

字体必须随工程提供并由 XML 声明，不依赖开发机字体；原许可也应放入工程。新剧本 7、UI 2、存档 6、KPAK 1 是不同格式版本，项目的 `content-version` 由作者维护，不等于程序版本 0.7.2。

## 3. 两种模式与播放器参数

| 项目 | 工程模式 | 发布模式 |
| --- | --- | --- |
| 显式入口 | `--project <目录>`，别名 `--game` | `--package <文件>` |
| 内容来源 | 工程目录的只读快照 | KPAK 内的只读快照 |
| 保存内容修改后 | 监控、准备候选，验证成功才更新 | 当前游戏不变化，重新打包并重启才生效 |
| 工程状态窗 | 有，可查看错误与重载 | 无 |
| 用户存档/设置/CG | 独立用户数据目录 | 独立用户数据目录 |
| XML/JS 编写方式 | 同一套 API | 同一套 API |

Windows 发布正常启动只有游戏窗口，不附带或闪现命令行窗口；启动失败通过原生错误框报告。工程运行可复用父控制台，无父控制台且未重定向时创建工程日志窗口。`--check`/`--help` 只复用已有控制台，不新建窗口，重定向 stdout/stderr 与退出码仍可用。打包工具始终是控制台程序。

指定 `--project`、`--game`、`--package` 时只能选一个，不可重复或混用。显式工程参数优先于程序旁默认包。

未指定内容入口时，程序先寻找 **exe 所在目录** 的 `game.kpak`，存在即进入发布模式；包损坏直接失败。没有这个文件时才尝试编译时记录的源码根 `games/demo`。因此便携发布目录必须包含 `game.kpak`，不能依赖开发机的源码目录。当前工作目录中的同名包不会被自动选择，需用 `--package` 指定。

### 3.1 参数参考

| 参数 | 默认/行为 |
| --- | --- |
| `--project <目录>` | 工程模式，入口为该目录下的 story.xml；正常运行启用监控 |
| `--game <目录>` | `--project` 的别名 |
| `--package <文件>` | 发布模式，读取指定 KPAK，不监控目录 |
| `--renderer auto` | 默认；优先硬件 D3D11，不能建立硬件设备时使用 WARP 窗口及 CPU 像素算法 |
| `--renderer d3d11` | 启动必须建立硬件 D3D11；运行中像素操作失败仍可保护性回退 CPU |
| `--renderer cpu` | 强制 CPU 滤镜/Live2D 合成；Windows 窗口仍通过 D3D11 呈现，必要时使用 WARP |
| `--check` | 验证内容和资源后退出，不进入游戏、不启动监控、不写用户数据；默认不打开窗口/GPU/音频设备 |
| `--cubism-core <DLL>` | 显式指定受信任的 Cubism Core 动态库 |
| `--no-live2d` | 显式显示立绘的静态替代图；仍读取检查模型相关资源，不能绕过缺图/缺文件 |
| `--no-audio` | 禁用音频设备输出，仍加载/解码音频和视频音轨 |
| `--save-dir <目录>` | 指定独立用户数据目录，包括剧情槽、设置与 CG；不再附加 story_id 子目录 |
| `--help` / `-h` | 打印帮助并退出 |

`--check --renderer d3d11` 在 Windows 上额外验证硬件设备和 HLSL 编译。`--renderer cpu` 是像素后端选择，不是无 D3D11 窗口模式；也不等于 `--no-live2d`，CPU 模式仍可运行真实模型。

播放器现在是 Windows GUI 程序，PowerShell 直接调用 exe 可能立即返回提示符。在自动化脚本中要等待 `--check` 并读取退出码时，可将输出接入管道：

```powershell
./target/release/kakera-avg.exe --project games/demo --check | Out-Host
if ($LASTEXITCODE -ne 0) { throw '内容检查失败' }
```

也可用 `Start-Process -NoNewWindow -Wait -PassThru` 并读取返回对象的 ExitCode；`cargo run ... --check` 自身会等待子进程。参见 [Microsoft PowerShell 进程说明](https://devblogs.microsoft.com/powershell/managing-processes-in-powershell/) 与 [Start-Process 参数](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process)。普通玩家启动无需等待脚本，也无需显示控制台。

检查示例：

```powershell
./target/release/kakera-avg.exe --project games/demo --check --renderer d3d11 | Out-Host
./target/release/kakera-avg.exe --project games/demo --renderer cpu --no-audio --save-dir target/cpu-saves
```

`--check` 包含 XML 严格校验、脚本注册、初始条件与入口生命周期、字体/图像/音频/视频/模型准备；不穷举动态 JS 路由或所有按钮。静态检查成功后仍需实际验证中文、分支、媒体、菜单暂停和退出重启后的读档。

### 3.2 Core 查找顺序

有 Live2D 且未显式禁用时，需要真实 Core；没有模型时不要求提供该 DLL。

1. `--cubism-core <DLL>`。
2. 环境变量 `CUBISM_CORE`。
3. 当前运行 exe 旁的 `Live2DCubismCore.dll`。
4. 仅工程模式及 kakera-pack：源码根固定的 `runtime/live2d/windows-x64/Live2DCubismCore.dll`。

发布模式不会回退第 4 项。命令行或环境变量已指定的坏路径应直接修正，不会自动跳过改用后面的 DLL。模型和贴图在 KPAK 内，Core 是包外宿主依赖；XML/JS 不能指定或加载任意原生库。

## 4. 工程模式的日常编辑

启动 `--project` 后，展开左上角“工程状态”可查看监控状态、像素后端、错误和两个操作按钮。

1. 修改 XML、JS、PNG/JPEG、字体、音频、视频或模型文件并保存。
2. 原生文件通知经过约 200ms 去抖，再构建固定快照，解析和准备全部候选资源。
3. 宿主核对构建期间的工程指纹，并验证当前 Session 的变量、历史、可用选项、进入命令和媒体。
4. 成功后一次替换；旧内容在准备期间继续使用，过期候选不提交。

200ms 是去抖时间，加载大字体、视频或模型会延长等待。它不是增量补丁系统：候选按完整工程准备，而非仅重读改动的一行。

### 4.1 更新成功后哪些状态保留

| 状态 | 结果 |
| --- | --- |
| 剧情位置、变量与历史 | 通过新内容完整校验后保留 |
| 当前台词 | 使用新文本并直接补全 |
| UI 页面栈和 UI 局部变量 | 按新 XML 初值与当前 game.enter 重新建立，不保留打开的菜单 |
| 自动播放 | 停止 |
| 视频、模型、音频 | 重建当前声明状态；视频从起点播放 |
| 转场和 JS 瞬时动作 | 当前显示恢复为最终态，不重播；之后的正常进入仍从当前画面转场 |
| 设置、CG、磁盘存档 | 不因热更新写自动档或重复 CG 解锁；现有偏好/进度继续由独立文件管理 |

`game.enter` 会参与候选校验与 UI 状态刷新，但热更新不执行新增持久解锁或瞬时动画。不要用回调调用次数、JS 全局变量或 UI 局部变量记录剧情进度；剧情状态放在 story 的变量中。完整权限见 API 第 11、20 节。

### 4.2 错误与不兼容修改

- XML/JS 语法错误、缺失素材、坏媒体或进入命令校验失败：显示“更新失败，继续使用旧内容”，保留旧 Session、音频和画面。修复保存后自动重试，也可点击“重新验证资源”。
- 新内容合法但与当前历史/变量不兼容：保留旧进度和候选；作者确认需要放弃当前内存进度时，点击“从入口重新载入（丢弃当前进度）”。
- story_id 已改变：须重启并选择独立用户数据目录，工程窗不会强行切换故事身份。
- 初次启动就有错误：尚无旧内容可以保留，程序报错退出；先修正工程并重新启动。

改变场景 ID、变量类型/范围或历史路由时，应评估旧存档并显式提升 `content-version`。从入口重新载入不迁移磁盘旧档，也不清空 CG/设置文件；新契约与旧档不匹配时，旧档会被拒绝。

## 5. kakera-pack 完整用法

```text
kakera-pack <工程目录> <输出.kpak> [--force] [--level 1..22]
            [--cubism-core <DLL>] [--no-live2d]
```

工程与输出是两个必填位置参数；选项写在它们后面。推荐使用 `.kpak` 后缀，自动发现要求包名为 `game.kpak`。工具不提供解包、资源列表、增量打包或上传命令；当前也没有 `--help` 选项，不带参数会打印用法并以失败状态退出。

### 5.1 参数与示例

| 参数 | 说明 |
| --- | --- |
| `<工程目录>` | 已存在的完整内容目录，必须含 story.xml |
| `<输出.kpak>` | 输出文件；父目录可自动创建，输出必须位于工程目录外 |
| `--force` | 允许覆盖已有输出；通过全部校验后原子替换，失败保留旧包 |
| `--level <1..22>` | Zstandard 压缩级别，默认 19；较高不保证每种素材都明显变小，通常耗时/内存更多 |
| `--cubism-core <DLL>` | 打包校验使用的真实 Core，查找默认规则见第 3.2 节 |
| `--no-live2d` | 不加载 Core，仍检查模型文件结构/贴图等；不等同于真实 Core 参数与动作验证 |

```powershell
# 首次生成：输出在 games/demo 之外
./target/release/kakera-pack.exe games/demo target/demo-release/game.kpak

# 快速迭代；覆盖现有包
./target/release/kakera-pack.exe games/demo target/demo-release/game.kpak --force --level 1

# 使用更高压缩级别；显式检查真实模型
./target/release/kakera-pack.exe games/demo target/demo-release/game.kpak --force --level 22 --cubism-core runtime/live2d/windows-x64/Live2DCubismCore.dll
```

以下输出位置不合法，因为在输入工程内部：

```powershell
./target/release/kakera-pack.exe games/demo games/demo/game.kpak
```

`--no-live2d` 只是本次工具的校验方式，不会删除模型、把模型烘焙为图片或写入永久禁用标志。之后正常启动该 KPAK，仍需 Core；要选择静态替代图，播放器也需显式传 `--no-live2d`。打包工具不接受播放器的 `--renderer`、`--check`、`--save-dir` 或 `--no-audio` 参数。

### 5.2 收集范围与排除规则

工具先从 story.xml 沿 next 读取并合并全部剧本，以单个 story.xml 写入包，移除链上其余源章节 XML。UI XML、JS 和素材保持原路径；不会改写磁盘工程。next 只决定装配顺序，跨章场景仍由 JS 通过 frame ID 路由。

其余内容递归收集工程根下所有未排除的普通文件，**不只收集 XML 引用的文件**。链外 XML 也按普通文件收集，不会因扩展名误删 UI；剧本文件必须显式接入链才参与合并。未使用的大图、旧视频、设计源文件或手动备份也可能进入包，应放在工程根之外；没有自定义 ignore 文件或 include/exclude 参数。

| 类别 | 排除名称 |
| --- | --- |
| 目录 | `.git`、`.idea`、`.vscode`、`target`、`saves`、`node_modules` |
| 临时/备份名称 | 以 `.tmp` 或 `~` 结尾 |
| 用户数据名称 | `settings.json`、`profile.json`、`save.json`、`slot-*.json`、`auto-*.json` |

这些名称规则按名称精确匹配，不是任意备份文件识别器，适用于树内各级。不要把正常剧情素材放在保留路径；引用被排除的文件会导致资源缺失。许可文件正常收集；工具不会凭文件扩展名自动排除 DLL/EXE，因此原生库应按发布目录规范放在工程外。

### 5.3 校验、输出与失败行为

打包顺序为：收集固定快照 → 完整剧本链/资源及入口计划校验 → 合并为单个 story.xml 并移除链上源章节 → 排序/去重/压缩 → 解码自检并独立验证包内故事 → 再扫描确认工程指纹未变 → 同目录临时文件及原子提交。

退出码 0 表示成功；失败为 1，错误写入 stderr。输出示例：

```text
剧本合并：5 个 XML → story.xml
打包完成：target/demo-release/game.kpak
69 文件，原始 27674393 字节，资源包 21555905 字节（77.9%）
```

以上为 demo 的一次级别 19 结果，不是所有工程的压缩承诺。百分比是“包大小 ÷ 原始文件总字节”，越低越小；重复内容共享块，整体 solid Zstandard 压缩。PNG/MP4 不做有损转码。同一工程字节、同一级别及同一工具实现可确定性生成相同包，不记录时间戳。

校验失败、工程在校验时改变、压缩失败或提交失败都不会先删除旧包。新建的输出父目录可能保留；工具不会自动清理失败目录。未传 `--force` 时已有输出直接拒绝。

### 5.4 包预算

| 项目 | 上限 |
| --- | --- |
| 包内文件数 | 10000 |
| 剧本链文件数 | 128，每份都需要显式 next |
| 剧本 XML 字节 | 源文件累计与合并结果分别不超过 16MiB |
| 逻辑路径 | 1024 UTF-8 字节 |
| 单文件原始字节 | 128MiB |
| 压缩帧、解压 payload | 分别不超过 512MiB，外层另有 64 字节头 |
| 按文件累计的原始总字节 | 512MiB；去重不豁免逻辑总量 |

图片解码、字体、音频/视频、模型还有各自预算，以 API 对应章节为准。包不加密，不提供防提取或来源认证；SHA-256 用于损坏检测。加载时整体解压为受限内存快照，不逐文件解包到游戏目录，也不提供大包按需流式读取；实际进程内存还包括解码资源和 GPU 缓存。

## 6. 制作完整发布目录

### 6.1 使用仓库发布脚本

```powershell
# 默认 demo，默认 target/package/kakera-avg-v0.7.2
./tools/package.ps1

# 自定义工程与新的输出目录
./tools/package.ps1 -Project games/my-game -Output target/package/my-game-v1 -CompressionLevel 19
```

脚本先把工作目录切到仓库根，所以相对的 `-Project`/`-Output` 都以仓库根为基准。参数为：

| 参数 | 默认值/行为 |
| --- | --- |
| `-Project` | `games/demo` |
| `-Output` | `target/package/kakera-avg-v0.7.2`；目标已存在即拒绝，包括已有空目录 |
| `-CompressionLevel` | 19，范围 1–22 |

脚本构建两个 release 二进制，再调用 kakera-pack，复制播放器、KPAK、仓库固定 Core、素材/依赖许可证及手册。它没有 `--force`、`-CubismCore` 或 `-NoLive2D` 参数；固定 Core 必须存在，即使项目不使用模型也会复制。打包失败会保留已建立的输出目录供诊断；重新运行应选新的输出目录。

生成目录大致如下：

```text
my-game-v1/
  kakera-avg.exe
  game.kpak
  Live2DCubismCore.dll
  README.md
  licenses/
  doc/
```

没有 `games/` 散装资源、开发存档或 kakera-pack.exe；打包工具保留在 `target/release` 供作者使用。游戏里的字体/模型许可在包内，脚本也将 `assets/licenses` 复制到包外 `licenses/game`。本地生成目录不执行网络上传。

### 6.2 手动组装

需要选择其他宿主 Core 或不带 Live2D 的目录时，可手动创建新的发布目录，将 `kakera-avg.exe`、工具生成的 `game.kpak`、所需 Core 和相应第三方许可放入，保留随内容的字体/模型许可与文档。不使用模型时可省略 Core；有模型并采用真实 Live2D 时 DLL 必须放在宿主查找位置，不能只塞进 KPAK。

测试便携运行应从源码目录以外启动：

```powershell
# 路径替换为实际发布目录；不传 --project/--package/Core，验证自动发现
& "D:/releases/my-game-v1/kakera-avg.exe" --check --renderer d3d11 | Out-Host
& "D:/releases/my-game-v1/kakera-avg.exe" --save-dir "D:/AVG Saves/my-game-release-test"
```

若宿主环境设置了 `CUBISM_CORE`，它优先于程序旁 DLL；测试时应核对该值，避免误以为验证了旁置依赖。带空格的 exe 路径在 PowerShell 中用 `&` 调用。

### 6.3 更新已发布内容

先停止用于验收的播放器，修改工程，生成新 KPAK，检查后放入新的发布目录再启动验收。只更新现有包文件时需 kakera-pack 的 `--force`；整个目录更新则使用发布脚本的新 `-Output`。已经运行的游戏持有旧快照，替换磁盘包不会立即刷新它。

资源包失败或损坏不会回退工程。内容契约不兼容时提升 `content-version`；不提供旧档自动迁移。发布之前应实际检查剧情分支、逐字与暂停、手动/自动读档、媒体和目标机器，而不只依赖 `--check`。

## 7. 用户数据与开发隔离

默认路径由 story_id 选择，Windows 通常为 `%LOCALAPPDATA%\kakera\kakera-avg\data\<story_id>`，以启动日志的“存档目录”为准。两种模式使用同一套规则：相同 story_id 默认共享数据，不按工程目录或 KPAK 文件名隔离。

| 数据 | 文件 |
| --- | --- |
| 手动槽 1–200 | `slot-1.json` … `slot-200.json` |
| 轮换自动槽 1–10 | `auto-1.json` … `auto-10.json` |
| 偏好设置 | `settings.json` |
| CG 解锁 | `profile.json` |

开发、CPU 测试和发布验收分别传不同 `--save-dir`，避免互相影响。读取故事槽不会回退独立设置或 CG；启动默认从入口开始，用户主动读档后恢复。正式资源包内不写用户数据，也不要手动将测试存档放入发布目录。

## 8. 常见问题

| 现象 | 处理 |
| --- | --- |
| next 报错/循环或重复 ID | 核对每份文件恰好一个 src 或 end="true"；路径相对游戏根，同类 ID 在全链唯一，诊断定位源章节 |
| 改 XML/JS 没变化 | 查看启动日志是否为工程模式、修改的是否为该工程；展开工程窗排查失败。发布模式必须重新打包并重启 |
| 工程窗显示“当前剧情与修改不兼容” | 检查变量/场景/历史路由与 content-version；需要新初值时显式从入口重载，不强行沿用坏历史 |
| 输出包必须位于工程目录之外 | 将输出改为仓库 target 或工程同级目录；工程根不要选整个仓库 |
| 输出已存在 | kakera-pack 显式传 `--force`；package.ps1 则使用新的 `-Output` |
| 校验期间工程改变 | 等编辑器/素材导出完成，再重新打包；暂停持续写入工程的外部工具 |
| 包特别大 | 检查未引用素材、设计源文件和普通备份；这些不会自动剔除。提高压缩级别不能代替整理工程 |
| 包里缺少资源 | 核对逻辑路径、大小写、资源登记与排除名称；保留模型的完整相对目录结构 |
| 发布检查缺少 Core | 确认实际 exe 旁 DLL、命令行和 CUBISM_CORE；源码 runtime 只对工程/打包工具兜底 |
| --no-live2d 后仍提示缺模型文件 | 该选项只禁用 Core 与真实显示，仍检查模型相关文件；恢复资源或移除对应声明 |
| 设置 --no-audio 仍报音频格式错误 | 该选项只关闭设备输出，资源解码仍必须通过；打包工具也没有此选项 |
| CPU 模式仍创建 D3D11 | 正常；CPU 只切换滤镜/模型合成，窗口仍使用 D3D11/WARP |
| 校验成功但交互失败 | 动态 JS 目标/按钮计划在执行时才校验；按提示中的 JS 栈/资源位置排查并实际回归该路径 |

本版验证见 [v0.7.2 验收记录](v0.7.2-validation.zh-cn.md)，多文件与无控制台发布见 [v0.7.1 验收记录](v0.7.1-validation.zh-cn.md)，此前渲染/媒体边界见 [v0.7 验收记录](v0.7-validation.zh-cn.md)。


## v0.7.2 操作与截图存档

默认 demo 支持背景左键继续、右键隐藏 HUD；HUD 隐藏时先左键恢复，再继续。菜单、按钮、禁用控件、滑条及滚动列表不会穿透推进；完成选项仍须明确选择。自定义方式见 [API 第 22 节](xml-js-api.zh-cn.md#22-v072-背景输入hud-与截图存档)。

手动和自动槽 JSON 内保留 saved_at_unix_ms，并新增可选 screenshot（320×180 PNG/Base64）。时间以查看存档时的系统本地时区展示。截图与剧情一个文件原子提交；不产生单独 PNG 文件，不把用户截图打入 KPAK。旧无截图 save 6 仍可加载。缩略图随当前十槽页/十个自动槽读取缓存，图像最多 256KiB，JSON 最多 2MiB。

Windows D3D11、CPU 像素模式与 WARP 窗口均从客户区捕获；不包括桌面或系统标题栏。手动槽优先使用同场景最近一次无菜单画面；自动槽等对应呈现版本出现后提交，进入转场首帧也属于真实画面。捕获失败时手动保存整体失败，自动保存保留已提交剧情/旧文件并停用；可在设置中重新开启。没有捕获提供者的其他宿主暂不支持 GUI 带图保存。

GPU 捕获缓存最多两幅、每幅 64MiB，正常帧仅 GPU 拷贝；真正保存时才读回/缩图/编码。截图不是无损全尺寸相册，文件内不保存逐字/视频/模型动画的精确恢复进度；读取仍遵循原存档的最终态与媒体规则。
