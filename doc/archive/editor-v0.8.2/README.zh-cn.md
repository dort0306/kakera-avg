## 三类能力的标记

- **已有**：已在当前仓库代码或文档中存在的接口；第四篇给出定位。历史验收记录不是本次重新测试。
- **编辑器拟实现**：作者体验、工程元数据、确定性编译器、模型服务管理等，当前都不存在。
- **播放器拟扩展**：帧级断点、运行时快照和结构化调试事件等，必须作为明确 Rust 宿主扩展开发，不能假装能由游戏 JS 实现。

第五篇和第六篇出现的协议名、命令名、字段及预算均为建议契约，不是已可调用 API。当前不能使用 `--debug`、`--start-frame`、`ctx.jump` 或 JS 行级调试；这些名称也不作为本方案的现有依赖。

## 核心决策

1. **一格是一幕，不是视频帧。** 分镜顺序用于编辑组织，剧情真正流转由 JS 路由决定；没有 FPS、隐式下一格或跨幕画面继承。
2. **XML/JS 是可交付源文件。** 编辑器读取它们建立带来源信息的编辑表示；支持的部分可双向编辑，任意 JS 保持代码块，不承诺无损反编译成条件图。
3. **AI 输出结构化提案，编译器输出代码。** 两者分离；作者看见场景、美术候选和差异，接受后生成、校验，再提交，失败不破坏工程。
4. **新建场景创建一次显式稳定 ID。** 这不更改引擎的缺省 ID/打包 UUID 行为；导入无 ID 内容时提示其跨构建存档风险，提供显式固定 ID 操作。
5. **编辑器数据、模型和游戏内容分目录。** 现有打包器不是按资源引用裁剪，它可能收集任意未排除文件；不能把模型或编辑器索引放入游戏根再期待自动排除。
6. **先复用再扩展。** 先用现有库校验和外部真实播放器试玩，之后才开发受约束的帧级调试宿主；不为编辑器引入旧 schema 或 flow.xml。
