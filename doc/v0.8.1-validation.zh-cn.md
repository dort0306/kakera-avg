# v0.8.1 KPAK 2 验收记录

日期：2026-10-25。依据 [实现策略](v0.8.1-implementation-plan.zh-cn.md) 与 [KPAK 1/2 规范](kpak-format.zh-cn.md)。版本 0.8.1；story 8 / UI 3 / save 8 / demo content-version=8 不变。用户明确要求保留 KPAK 1 容器兼容，未恢复旧 story/UI/save 或旧档导入。

## 实现范围

- 新增 KPAK 2：80 字节固定头、64 位文件位置/长度、尾部受限索引、独立 1MiB 原文 Zstandard 块、块级去重和 SHA-256、索引 SHA-256。打开仅加载头和索引，访问时逐块验证后交付，每流只保留当前块，不整包解压、mmap 或保留全部块缓存。
- 新增 Archive 自动按版本选择 KPAK 1/2。KPAK 1 字节布局、生成器和小包预算保留，未知版本/坏头不回退目录。
- kakera-pack 默认 2，--format 1 显式小包；tools/package.ps1 默认 KPAK 2，新增 -Format 1|2，默认输出目录更新为 v0.8.1。
- ContentSource 增加 open/copy_to；目录与 KPAK 2 覆盖为真实流，原 read 仍有 128MiB 上限。视频流复制至后端临时 MP4，不再用整视频 Vec；原尺寸、时长、数量、PCM 和模型/图像缓存预算不放宽。
- 工程启动/热更与 KPAK 2 打包使用私有磁盘固定快照，流式复制/哈希并复查完整源指纹。打包只在暂存合并剧本，完整包扫描和独立资源加载成功后原子提交，失败保留旧包。不改源工程，不在绘制做 IO。
- 文件流与解压是 XML/JS 无法提供的宿主能力，因此扩展 Rust 内容边界；本轮无剧情或界面脚本 API 改动，AGENTS 已记明包兼容例外和 XML/JS 优先约定。

## 实际大文件与内存

单独测试进程执行 large_content_exceeds_kpak1_limits_without_whole_file_or_package_buffers：

- 生成 600MiB+37 字节的文件（629145637 字节），使用块内难压缩数据及不同块标记，不能凭高重复率把物理包缩成小文件。
- 磁盘固定快照、打包、全部唯一块自检、源指纹复查、完整流复制和尾字节核对通过；原 read 内存入口明确拒绝该大文件。
- 实际 KPAK 2 文件 629196870 字节，602 个唯一块，实际文件和单成员均超过 KPAK 1 的对应上限，非稀疏包或仅伪造逻辑长度。
- 独立 debug 测试进程每 200ms 采样 PeakWorkingSet64，峰值 12738560 字节，约 12.1MiB，耗时 133.40 秒。该数字只描述本容器测试进程，不包含操作系统文件缓存、其他进程或完整游戏的解码缓存，不是通用性能承诺。
- 本轮另先运行过 600MiB 高重复率内容，原文流读取成功，包 2768 字节，采样峰值约 12.3MiB；最终以难压缩、实际大包结果作为主要证据。

容器硬上限为包/逻辑总量 1TiB、单文件 64GiB、100000 文件、1048576 唯一块、索引 128MiB。没有实测 4GiB 以上实际包或 1TiB 极限；64 位格式和算术/边界检查不能替代这些实机容量测试。

## 验证边界

普通打开只保证索引和已访问块，未读取资源的损坏可能延后发现；完整 --check 才扫描全部唯一块。这是按需读取的明确约定。

本版没有实现所有图像/音频/模型的场景级惰性解码。播放器仍预先准备已声明资源，视频仍需流复制完整临时文件、预解码音轨，需要临时磁盘空间和启动时间；不宣称直接从包 seek 播放、网络流、提高视频时长/PCM 预算、加密或签名认证。

本轮无 GUI 布局/窗口交互改动；已运行真实媒体准备、Core 和 GPU/CPU 自动回归，没有重新做完整 GUI 视频暂停/结束/跳过、跨进程手动档/截图、Ctrl 持续按住、全部热更可见编辑等人工矩阵，也未复测设备音频流或主观听感。相关旧版本 GUI 记录仅作历史，不能作为本轮复测。其他平台和更大规模的索引/数据集仍未实机验收。
